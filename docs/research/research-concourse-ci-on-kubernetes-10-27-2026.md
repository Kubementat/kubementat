# Research: Concourse CI on Kubernetes as an optional Kubementat CI/CD engine

- Date: 2026-10-27
- Scope: installing and running Concourse CI on Kubernetes with the official Helm chart, and adding it to Kubementat as an optional CI/CD component next to Tekton. Includes a mapping from the existing Docker Compose automation (`kwisatz/tasks/setup-concourse.sh`).
- Method: primary sources only where possible. Sources were GitHub releases, issues and PRs read through the GitHub API, the chart package and repo index, the concourse-ci.org docs, Docker Hub manifests and Kubementat's own source. The chart was rendered, schema-validated and **installed on a throwaway kind cluster**, and a real pipeline was run (section 9). All versions were read on 2026-10-27.
- Markers: **[verified]** means checked against a primary source or by running the software. **[inference]** means my own judgement. **[unverified]** means I could not confirm it.

## 1. Executive summary and recommendation

**Recommendation: add Concourse as an opt-in helmfile release using the official chart `concourse/concourse` 20.3.2 (Concourse 8.3.2).** Run it in its own `concourse` namespace with privileged StatefulSet workers and the containerd runtime. Use the chart's built-in Kubernetes credential manager, with one `concourse-<team>` namespace per Kubementat team. Generate the keys with the existing `CryptoUtils` (Python `cryptography`) and store them git-crypt-encrypted in `platform_config/<env>/kubementat_components/concourse/`. Keep Tekton as the default engine.

Why this works for Kubementat:

| Requirement | Finding |
|---|---|
| FOSS, no lock-in | Apache-2.0 for Concourse and the chart. The project is part of the Cloud Foundry Foundation. Its main developer is Pixel Air IO, led by maintainer Taylor Silva [verified, 2.2] |
| Alive and maintained | 14 releases since v8.0.0 (2026-01-15). The latest is **v8.3.2 (2026-10-23)**. The chart follows each release within hours [verified, 2.1] |
| ARM64 / Raspberry Pi | Official multi-arch (amd64 and arm64) images since v7.14.0 (2025-08). This covers `concourse/concourse`, the bundled resource types and `oci-build-task`. There are arm64 `fly` and `concourse` tarballs too. No 32-bit ARM support [verified, 2.3] |
| No Bitnami dependency | Chart 19.0.0 (2025-09-15) dropped the Bitnami PostgreSQL subchart for a plain `postgres:17` StatefulSet. The chart says that StatefulSet is not for production [verified, 4.4] |
| Works on Kubernetes | **Verified end to end on kind**: worker registration with keys generated by Python, `fly` downloaded from the web node, login as a local user, the Kubernetes credential manager, cluster DNS and egress from tasks, a privileged `oci-build-task` BuildKit build, and worker retirement on `kubectl delete pod`. One kind-specific bug was found and worked around (next row) [verified, 9] |
| Pitfall found | On **kind**, every unprivileged task container fails with `error mounting "sysfs" ... operation not permitted`. Both runtimes are affected. The cause is kind's bind-mounts over `/sys/devices/virtual/dmi/id/product_{name,uuid}`, which the kernel's "mount too revealing" check rejects. A three-line `umount` entrypoint wrapper fixes it. This matters for Kubementat's e2e tests, not for real nodes [verified, 5.2] |

The main costs, and why Concourse stays optional:
- Workers must run **privileged**. The namespace therefore needs `pod-security.kubernetes.io/enforce=privileged`, and a worker is effectively root on its node. Treat CI nodes as a trust boundary (section 5.1).
- Concourse is not Kubernetes-native. Tasks run in containers nested inside the worker pod. Kubernetes neither schedules nor sees them, so resource limits, Goldilocks/VPA and Linkerd do not apply to them (section 5.3). Native Kubernetes scheduling was explicitly abandoned upstream in 2025 (#5682 "Not doing this").
- It needs a PostgreSQL database that you must back up. On a Raspberry Pi the built-in StatefulSet is enough. For anything you care about, use CloudNativePG (section 4.4).

**Version note for the kwisatz automation:** it pins `concourse/concourse:8.3.0`. **8.3.1 (2026-09-28) fixed two GitHub Security Advisories** (path traversal via parent-dir references, and the creds interface) as well as an overlay-driver crash loop. **8.3.2 (2026-10-23)** rebuilt everything after the eMudhra CA compromise. Bump to 8.3.2 there as well [verified, 2.1].

### 2.4 Changes from v7 to v8 that matter here [verified, 8.0.0 release notes [2]]

- **containerd is the default runtime on Linux workers** (#9372). Before v8 it was Guardian. The chart removed its own default runtime value in 2025-11 (#398), so the binary default applies. Upstream says only containerd and Guardian are for production on Linux. All future runtime work goes into containerd [7][8].
- Always on, and the flags are gone: pipeline instances, the `across` step, and secret redaction (`redact secrets is always enabled`; v8.2 added `CONCOURSE_DISABLE_REDACT_SECRETS` back as an opt-out). `put.inputs` defaults to `detect`. **[observation]** The chart still exposes `enableAcrossStep` and `enablePipelineInstances` with default `false`. They are vestigial; do not rely on them.
- fly no longer accepts `{{old_style}}` vars.
- Large DB migration: md5 hashing becomes sha256 on several tables. Upstream recommends `VACUUM FULL ANALYZE` afterwards on big databases. **[inference]** This is irrelevant for a fresh install. It matters if someone migrates an existing 7.x database.
- New since v8: `--oidc-issuer-url`, Go runtime metrics, containerd log level, S2 streaming compression, P2P fallback to ATC streaming.

### 4.3 Worker as StatefulSet versus Deployment [verified from chart + README]

- **StatefulSet**: a stable worker name (the pod name), a PVC per worker (`concourse-work-dir-<pod>`), `podManagementPolicy: Parallel` and a PodDisruptionBudget (`worker.minAvailable`, default 1). On a single-worker Pi set `minAvailable: 0`, otherwise node drains will block.
- **Deployment**: `ephemeral` is forced to true, the work dir is an emptyDir, and `persistence.enabled` is ignored. It suits autoscaled throwaway workers (there is an HPA template). Check emptyDir size and medium: overlay on top of an overlayfs root does not work, but kubelet emptyDirs sit on the node filesystem, which is fine.

### 4.4 PostgreSQL: the Bitnami change and its implications [verified]

- Bitnami moved most versioned images to `docker.io/bitnamilegacy` (no more updates) on 2025-08-28 and restricted free images to a small "latest-only" hardened set [11][12].
- Concourse reacted in **chart 19.0.0 (2025-09-15)**: *"Removed the bitnami/postgresql chart dependency (see bitnami/charts#35164) and replaced it with a StatefulSet that deploys the `postgres` image from Docker Hub ... Reminder that the PostgreSQL dependency has never been intended for production usage."* A migration guide is linked from PR #389 [13].
- The built-in StatefulSet uses `postgres:17` (multi-arch, verified), runs as a single instance, has no backups and no operator. Postgres 18 works from Concourse 8.3.0 onward (#9621). Upstream requires PostgreSQL 11 or later and recommends the latest. It also suggests *"at least a couple cores, ideally four to eight"* for busy installations [10].
- **For production use CloudNativePG** (operator chart `cnpg/cloudnative-pg` 0.29.1 = CNPG 1.30.1, Apache-2.0, multi-arch). It gives scheduled backups (Barman Cloud plugin to S3/MinIO), PITR, failover and `-rw` services. Wiring: `postgresql.enabled: false`, `concourse.web.postgres.host: <cluster>-rw.<ns>.svc`, `sslmode: require`, and credentials in `secrets.postgresUser/postgresPassword`. The chart reads them only from its own web Secret (keys `postgresql-user` and `postgresql-password`). Have Kubementat generate the DB password once and feed it to both the CNPG bootstrap secret and the chart values. Do not try to point the chart at CNPG's `<cluster>-app` secret.
- Caveat: issue #9543 (closed 2026-10-14) showed that live log streaming (LISTEN/NOTIFY) stalls after a DB failover. A fix was merged. Multi-host DSN support is still open as follow-up work. **[inference]** After a CNPG switchover, restart the web pods if logs stop streaming.

### 4.5 Secrets [verified]

- The chart's `values.yaml` contains **fixed, publicly known default keys** for `hostKey`, `sessionSigningKey` and `workerKey`, and `localUsers: "test:test"`. A Kubementat install must always provide its own (open chart issue #354 complains about this default).
- Required: `hostKey`, `hostKeyPub`, `sessionSigningKey`, `workerKey`, `workerKeyPub`, `localUsers`. Recommended: `encryptionKey` (16 or 32 chars), plus `postgresUser`/`postgresPassword` when using an external DB.
- Formats [14]: `ssh-keygen -t rsa -b 4096 -m PEM` produces a PKCS#1 `BEGIN RSA PRIVATE KEY`. `concourse generate-key -t rsa|ssh` is the alternative. Python `cryptography` with `PrivateFormat.TraditionalOpenSSL` plus `PublicFormat.OpenSSH` produces exactly that pair. Kubementat's `CryptoUtils.generate_ssh_key_pair()` already does this. **Keys generated this way registered a worker and signed sessions on 8.3.2** [verified, 9].
- `secrets.create: false` is the "bring your own Secret" mode. It needs two Secrets (`concourse-web` and `concourse-worker`) with exactly the chart's key names. For Kubementat, keeping `create: true` and supplying a git-crypt-encrypted values file is simpler and matches existing practice (the Gitea values already contain passwords).

### 4.6 Credential managers

**Kubernetes credential manager (default, recommended first)** [verified on kind]
- Team `T` reads from namespace `<prefix>T`. With `namespacePrefix: concourse-` that is `concourse-main`, `concourse-dev1` and so on. `((foo))` resolves to Secret `<pipeline>.foo`, then Secret `foo`, key `value`. Nested fields use `((foo.bar))`.
- The chart creates the namespaces (`createTeamNamespaces`), a ClusterRole with only `get` on `secrets`, and a RoleBinding to the web ServiceAccount in each team namespace. Shared secrets: `sharedNamespaceSuffix`, and from 8.3 `CONCOURSE_KUBERNETES_SHARED_PATH`.
- Upstream allows only one credential manager per Concourse: *"You can't use more than one credential manager at a time."* [9]. Var sources per pipeline (`var_sources`) are the escape hatch.

**Vault (Kubementat already ships it, group `extra`)** [verified docs; inference for the wiring]
- Paths `/concourse/<team>/<pipeline>/<secret>` then `/concourse/<team>/<secret>`, KV v1 or v2, with the policy `path "concourse/*" { capabilities = ["read"] }` [15].
- Auth backends Concourse supports: periodic token, AppRole, cert, userpass. It has **no Vault Kubernetes auth method of its own**. The chart has `concourse.web.vault.tokenPath` (→ `CONCOURSE_VAULT_CLIENT_TOKEN_PATH`), which is meant for a Vault Agent sidecar. The injector is enabled in Kubementat's Vault values. Using Vault Kubernetes auth with an Agent sidecar that writes `/vault/secrets/token` into the web pod therefore avoids static tokens. **[unverified end to end]**
- Recommendation: start with the Kubernetes credential manager, because it has no dependency on the `extra` group and matches the `kmt setup-secrets` pattern. Offer Vault as an option later.

### 4.7 What `helm uninstall` leaves behind [verified on kind]

- With `keepNamespaces: false` the team namespaces (`concourse-main`, `concourse-dev1`) **are deleted together with every secret in them**. With the default `true` they survive (`helm.sh/resource-policy: keep`).
- Left behind after uninstall: the release namespace `concourse` and **both PVCs** (`concourse-work-dir-concourse-worker-0` and `data-concourse-postgresql-0`). The ClusterRole is removed.

## 5. Best practices and pitfalls on Kubernetes

### 5.1 Privileged workers and Pod Security Admission
- Workers need `privileged: true` because they run containerd and nest containers [16]. The chart hardcodes it, and there is no rootless mode. `privilegedMode: fuse-only` (8.3) narrows what *privileged tasks* get, but the worker itself stays privileged.
- Label the namespace: `pod-security.kubernetes.io/enforce=privileged` (tested; a `baseline` namespace would reject the worker). Keep the rest of the cluster at `baseline` or `restricted`. **[inference]** Concourse is the only Kubementat component that needs this, so Polaris will flag it. Add an exemption.
- Isolation: a privileged task (for example `oci-build-task`) is effectively root on the node. In production, put workers on dedicated, tainted CI nodes (`worker.nodeSelector` + `tolerations` + `hardAntiAffinity`) and keep workloads with secrets elsewhere.

### 5.2 Kernel, cgroups and the kind sysfs issue
- Upstream minimum: kernel 5.15 (tested on Ubuntu 22.04/24.04), user namespaces enabled, memory and swap accounting enabled for task limits [8].
- **kind (found in this research) [verified]:** kind bind-mounts `product_name` and `product_uuid` over `/sys/devices/virtual/dmi/id/` in each node. Those mounts are inherited into privileged pods. Concourse's unprivileged task containers live in a user namespace. When they mount a fresh `sysfs`, the kernel refuses because the existing sysfs is partly covered (`mount_too_revealing`), so every `image_resource` check and task fails:
  `error mounting "sysfs" to rootfs at "/sys": ... operation not permitted`.
  This happened with both containerd and guardian on kind v0.33.0 (Kubernetes 1.37, containerd 2.3.4, host kernel 6.17, cgroup v2). Removing the mounts inside the worker container fixed it immediately. A persistent fix is a command wrapper (tested):
  ```yaml
  command: ["dumb-init", "sh", "-c",
    "for f in /sys/devices/virtual/dmi/id/product_uuid /sys/devices/virtual/dmi/id/product_uuid /sys/devices/virtual/dmi/id/product_name; do umount \"$f\" 2>/dev/null || true; done; exec /usr/local/bin/entrypoint.sh \"$@\"", "sh"]
  args: ["worker"]
  ```
  The chart has no `worker.command` value, so for e2e tests apply it with a helmfile `jsonPatches`/`strategicMergePatches` entry or `kubectl patch`. Do **not** enable it for real clusters. **[inference]** k3s/k3d and bare-metal nodes do not overmount `/sys` this way, which is why the kwisatz Docker setup works. Verify on k3d before relying on it.
- Raspberry Pi: enable memory cgroups (`cgroup_memory=1 cgroup_enable=memory` in `/boot/firmware/cmdline.txt`). The k3s docs require this and advise an external SSD instead of SD/eMMC [17]. Use a 64-bit OS. **[unverified]** The Pi 5 default 16K-page kernel has not been tested with Concourse's containerd/runc. Use the 4K kernel (`kernel=kernel8.img`) if anything misbehaves.

### 5.3 iptables versus nftables
- The 8.3.2 image ships both, but `/usr/bin/iptables -> xtables-legacy-multi` (iptables v1.8.13 legacy) [verified]. On kernels without the legacy `ip_tables`/`ip6_tables` modules, the containerd CNI bridge setup fails (`can't initialize ip6tables table 'nat'`, #9449). The issue was closed on 2026-10-05 as fixed by image packaging, and the in-code nft PR #9746 was withdrawn. It worked on kind (Debian trixie node). Community workaround: install `iptables-nft`/`iptables-wrappers`, or switch the symlink in a wrapper entrypoint. **[unverified]** Raspberry Pi OS and Fedora/RHEL 10 nodes are untested.

### 5.4 Storage and baggageclaim
- Use `overlay` on a real local filesystem (ext4 or xfs PVC from `local-path` or local SSD). Avoid NFS or network block storage for the work dir (slow, and overlay may not work on NFS). Avoid btrfs on kind (#8603).
- The work dir is cache. Combine `cleanUpWorkDirOnStart: true` with PVC `Delete` policies. Size it for images plus caches: 20Gi works on a Pi, use 100Gi+ in production.
- The 8.1 to 8.3 releases fixed several overlay volume leaks and an in-place-restart mount explosion (#9722). Stay on 8.3.1 or later.

### 5.5 Worker lifecycle on Kubernetes
- Pod deletion: the preStop hook sends `SIGUSR2` (retire) every 60 s until the process exits. Verified: a worker with 7 containers retired, was marked "retired" by the ATC collector and came back under the same name in about 50 s.
- Set `terminationGracePeriodSeconds` longer than your longest build (600 s or more), otherwise Kubernetes SIGKILLs the pod and leaves a **stalled** worker. Fix that with `fly prune-worker -w <name>`, or set `stalledWorkerTimeout` (8.3) to prune automatically. Chart issue #81: the preStop hook can exit with 137 and slow down `kubectl delete pod`.
- PodDisruptionBudget: the default `minAvailable: 1` blocks `kubectl drain` on single-worker clusters. Use `0` there.
- Upgrades restart workers, which retire and then lose their caches. Expect slower first builds after an upgrade.

### 5.6 External URL, tunnels and fly
- `externalUrl` defines the OIDC issuer and the token endpoint that `fly login` posts to. With `externalUrl=http://127.0.0.1:8080` and a tunnel on another port, `fly login` failed with `resource not found` [verified]. The same failure happens when `localhost` resolves to `::1` and another process holds that port.
- Rule for Kubementat: tunnel mode uses `externalUrl = http://127.0.0.1:<tunnel-port>` and `fly -c http://127.0.0.1:<tunnel-port>` (never `localhost`). Ingress mode uses `https://concourse.<BASE_DOMAIN>`. `kmt tunnel-concourse` must use the same port the values declare.
- Download fly from the web node (`/api/v1/cli?arch=amd64|arm64&platform=linux`) so the client and server versions always match. The response is the raw binary.

### 5.7 Sizing [inference unless marked]

| Profile | Web | Worker | Postgres | Notes |
|---|---|---|---|---|
| Pi 4/5 8GB, k3s single node | 1 × 100m/256Mi req, 1Gi limit | 1 × 250m/512Mi req, 3Gi limit, 20Gi | built-in, 128Mi req, 512Mi limit, 4Gi | Cap `limitActiveTasks` at 2–4. Image builds dominate |
| Production-ish | 2 × 500m/512Mi, 2Gi limit | 3 × 2 CPU/4Gi req, 12Gi limit, 100Gi SSD | CNPG 3 instances, 2–4 CPU | Upstream says to add workers when the average container count nears about 200 per worker, and prefers smaller workers to a few large ones [8] |

The chart defaults are worker requests 100m/512Mi and postgres 250m/256Mi req with a 500m/512Mi limit [verified]. Task containers do not count against Kubernetes requests, so give workers generous memory limits to avoid OOM kills mid-build.

### 5.8 Network policies
Web needs ingress on 8080 (users), 2222 (workers) and 9391 (Prometheus), plus egress to Postgres and the Kubernetes API (credential manager). Workers need egress to web:2222, to registries and git, and, for deploy tasks, to the API server. With P2P streaming (`baggageclaim.bindIp: 0.0.0.0`) workers also talk to each other on 7788. Only the web pods should reach Postgres [10]. **[inference]** Start without NetworkPolicies, then add a default-deny with those allows in a later phase.

### 5.9 Workers outside Kubernetes
The chart supports `web`-only and `worker`-only releases. External workers (for example a Pi or a big build box running the kwisatz Docker worker) register by exposing `concourse-web-worker-gateway` (2222) through a `LoadBalancer`/NodePort and adding their public key to `secrets.workerKeyPub` or `teamAuthorizedKeys`. This avoids privileged pods in the cluster altogether. **[inference]** It is a good fit for security-sensitive production clusters.

### 5.10 Upgrades and backups
- Web nodes run DB migrations on start, guarded by a lock. *"We currently do not guarantee zero-downtime upgrades"* [18]. Procedure: back up the DB, read the "Breaking Changes" section, `helmfile apply` (the migration runs in an init container), then `fly sync`.
- Backups: CNPG ScheduledBackup with the Barman Cloud plugin. For the built-in StatefulSet, a CronJob running `pg_dump` into a PVC or S3. What is worth keeping: pipelines (also in git through `set_pipeline`), build history and logs, and encrypted credentials. **[inference]** If every pipeline is set from git, losing the DB on a dev cluster costs only history.

## 7. Kubementat integration design

### 7.1 Principles
- **Opt-in.** Concourse gets its own helmfile group `concourse`, so neither `standard` nor `extra` pulls it in by accident. `kmt install --helmfile-installation-group concourse` (or a new `--enable-concourse` flag) installs it. Tekton remains the default.
- **Convention over configuration.** The namespace is `concourse`, team namespaces are `concourse-<kmt-team>`, the hostname is `concourse.<BASE_DOMAIN>`, and keys are generated on first install and reused afterwards.
- **Secrets in git-crypt**, generated by Python. This mirrors `generate_linkerd_certs.sh` (keys under `platform_config/<env>/kubementat_components/linkerd/*.encrypted.*`), but in Python.

### 7.2 Files

| Path | Purpose |
|---|---|
| `templates/environment/kubementat_components/concourse/concourse_values.encrypted.yaml.template` | Small, Pi-capable default values (8.2). Copied by `kmt initialize`. Encrypted by convention |
| `platform_config/<env>/kubementat_components/concourse/concourse_secrets.encrypted.yaml` | **Generated** by `kmt concourse-generate-secrets` (no template; never committed unencrypted; `.gitattributes` already covers `*.encrypted.*`) |

### 7.3 Key and secret generation (Python port of the `ssh-keygen` logic)

Reuse `CryptoUtils.generate_ssh_key_pair(key_size=4096)`. Its output format matches `ssh-keygen -t rsa -b 4096 -m PEM` and was verified working. The logic should look like this:

```python
# src/kubementat/concourse_utils.py (sketch)
import secrets, string, yaml, os
from kubementat.crypto_utils import CryptoUtils

ALPHABET = string.ascii_letters + string.digits

def _password(n=32):
    return "".join(secrets.choice(ALPHABET) for _ in range(n))

def generate_concourse_secrets(path, admin_user="admin", external_db=False):
    """Idempotent: an existing file is the source of truth (like kwisatz reusing .env)."""
    if os.path.exists(path):
        return yaml.safe_load(open(path))
    host, host_pub = CryptoUtils.generate_ssh_key_pair(key_size=4096)
    session, _ = CryptoUtils.generate_ssh_key_pair(key_size=4096)
    worker, worker_pub = CryptoUtils.generate_ssh_key_pair(key_size=4096)
    admin_pw, db_pw = _password(), _password()
    values = {"secrets": {
        "hostKey": host, "hostKeyPub": host_pub.strip(),
        "sessionSigningKey": session,
        "workerKey": worker, "workerKeyPub": worker_pub.strip(),
        "localUsers": f"{admin_user}:{admin_pw}",   # plaintext is fine: file is git-crypt'd; bcrypt optional
        "encryptionKey": _password(32),
    }}
    if external_db:
        values["secrets"] |= {"postgresUser": "concourse", "postgresPassword": db_pw}
    else:
        values["postgresql"] = {"auth": {"password": db_pw}}
    with open(path, "w") as f:
        yaml.safe_dump(values, f, sort_keys=False)
    os.chmod(path, 0o600)
    return values
```

- Rotation: `kmt concourse-generate-secrets --rotate worker` regenerates one pair. Rotating the session key logs everyone out. Rotating the host or worker key needs a web and worker restart, which `helmfile apply` triggers through checksum annotations. **[unverified]** I did not check whether the chart sets checksum annotations. If not, add `kubectl rollout restart`.
- bcrypt for `localUsers` works (tested) but adds the `bcrypt` dependency. **[inference]** It is not worth it, because the value sits in a git-crypt file and a Kubernetes Secret anyway.

### 7.5 Multi-team mapping

| Kubementat | Concourse | Kubernetes |
|---|---|---|
| Environment `dev` | One Concourse install (`concourse` namespace) | |
| Admin | Team `main`, local user `admin` | `concourse-main` (shared and admin secrets) |
| Team `dev1` (`platform_config/dev/dev1/static.json`) | Team `dev1` (`fly set-team`) | **`concourse-dev1`** for credentials. The pipeline's deploy target stays `APP_DEPLOYMENT_NAMESPACE` (`dev1`) |
| Team helm-deployer SA (`HELM_DEPLOYER_SERVICE_ACCOUNT_NAME`) | `((kubeconfig))` secret in `concourse-dev1` with a token bound to the team's SA and RoleBindings only in `dev1` | Reuses `_setup_pipelines_setup_role_bindings` logic |

The helmfile template reads the team list. Either `kmt` writes `CONCOURSE_TEAMS` into `static.json`, or the template lists `platform_config/<env>/*/static.json` (helmfile has no glob function, so the first option is simpler). **[inference]**

Deploy credentials: tasks run inside the worker, **not as a Kubernetes ServiceAccount**. To deploy, a task needs an explicit kubeconfig or token (from `concourse-<team>`) pointing at `https://kubernetes.default.svc`, scoped to the team's app namespace. This differs from Tekton, where the TaskRun runs as `helm-deployer-sa`.

```yaml

  check_every: 1h

- name: app-image
  type: registry-image
  icon: docker
  source:
    repository: ((docker-registry-base-url))/((app-image-name))
    username: ((registry-username))  # Secrets registry-username / registry-password (key: value) in concourse-dev1
    password: ((registry-password))

- name: ci-image
  type: registry-image
  source:

    tag: latest

jobs:
- name: build
  plan:
  - get: app-src
    trigger: true
  - task: build
    privileged: true                 # oci-build-task (BuildKit) still requires it
    config:
      platform: linux
      image_resource:
        type: registry-image
        source: {repository: concourse/oci-build-task, tag: "0.15.8"}
      inputs: [{name: app-src}]
      outputs: [{name: image}]
      caches: [{path: cache}]
      params:
        CONTEXT: app-src
        # IMAGE_PLATFORM: linux/arm64,linux/amd64   # multi-arch, sets OUTPUT_OCI
      run: {path: build}
  - put: app-image
    params:
      image: image/image.tar
      additional_tags: app-src/.git/short_ref

- name: deploy
  serial: true
  plan:
  - get: app-src
    passed: [build]
    trigger: true
  - get: app-image
    passed: [build]
    params: {skip_download: true}
  - get: ci-image
  - task: helm-upgrade
    image: ci-image
    config:
      platform: linux
      inputs: [{name: app-src}, {name: app-image}]

Also: `put` steps now default to `inputs: detect` (v8). In the production values (8.3) the Ingress `hosts` are supplied by the helmfile release layer (8.1). The chart refuses to render an enabled Ingress without hosts.

A smaller smoke pipeline was run as written in section 9. It covered the credential manager, DNS and egress, and an oci-build-task build.

### 7.8 Uninstall implications (`kmt uninstall`)

- Add `concourse` to `DEFAULT_NAMESPACES`. The existing sweep (`namespaces_kubementat_owns` → `_uninstall_helm_releases` → `_delete_claims_in` → namespace delete) then removes the release, the **two retained PVCs** and the namespace. This matters because `helm uninstall` alone leaves both PVCs (4.7).
- Team credential namespaces `concourse-<team>`: extend `_team_namespaces()` (or add a component hook) to include `f"{prefix}{team}"` plus `concourse-main`. With `keepNamespaces: false` Helm already deletes them, but the sweep should not rely on that.
- Cluster-scoped objects: the ClusterRole `concourse-web` is removed by Helm (verified). There are no CRDs, so `CRD_GROUPS_KUBEMENTAT_OWNS` is unchanged.
- The residue check ("DONE is earned") should look for `concourse*` namespaces and PVCs labelled `app=concourse-worker`/`app=concourse-postgresql`. Leave `platform_config/.../concourse/` (git) and the user's `~/.flyrc` targets alone. Optionally offer `fly -t kmt-<env> logout`.

### 7.9 Test and verification approach

1. **Unit:** key generation round-trip (load with `cryptography`, check the `BEGIN RSA PRIVATE KEY` and `ssh-rsa ` prefixes), idempotency (a second call reads, not regenerates), `helmfile template` snapshot for the concourse release.
2. **Static:** `helm template … | kubeconform -strict` (as in section 9; 43 resources valid).
3. **e2e on kind** (the CI lane): kind cluster → label the namespace privileged → `helmfile apply -l component_name=concourse` **with the sysfs `umount` patch (5.2)** → wait for `/api/v1/info` → `kmt concourse-install-fly` → `kmt concourse-login` → create a secret in `concourse-main` → set and trigger the smoke pipeline → assert `succeeded` → `kubectl delete pod concourse-worker-0` and assert the worker retires (not stalls) → `kmt uninstall` and assert no `concourse*` namespaces or PVCs remain. Measured on this machine: chart install about 80 s, smoke pipeline about 1–2 min.
4. **k3s/k3d lane** (preferred for the Pi story): the same steps without the patch. This would prove the "no sysfs overmount" assumption [unverified].
5. **arm64:** a manual or self-hosted Pi 5 (k3s) run of the same e2e before declaring Pi support.

## 11. Risks

| Risk | Likelihood / impact | Mitigation |
|---|---|---|
| Privileged workers = root on the node | Certain / high | Dedicated tainted CI nodes, privileged PSA only on `concourse`, external workers for sensitive clusters (5.9). Keep Tekton as the default |
| Maintainer concentration (one lead, one company) | Medium / high | It is Apache-2.0 under the CFF and easy to fork. Keep Concourse optional so it can be dropped. Pipelines are YAML in git |
| kind e2e needs a sysfs workaround | Certain on kind / medium | The patch in 5.2. Prefer a k3d lane. Do not ship the patch to real clusters |
| nft-only node kernels break container networking | Low–medium / high | Test on target distros. Wrapper switching to `xtables-nft-multi`. Watch #9449 follow-ups |
| Chart ships known default keys and `test:test` | Certain if misconfigured / critical | Kubementat always generates and supplies secrets. Add a unit test that the rendered secret differs from the chart default |
| Built-in Postgres has no backups | Certain / medium | Fine for dev. CNPG for production |
| Task containers invisible to Kubernetes resource management (VPA/Goldilocks/limits) | Certain / medium | `limitActiveTasks`, generous worker limits, Concourse metrics in Grafana |
| `externalUrl`/tunnel mismatch breaks `fly login` | High for tunnel users / low | `kmt` derives both from one setting (5.6) |
| Stalled workers after hard kills | Medium / low | Long grace period, `stalledWorkerTimeout`, `fly prune-worker` in a runbook |
| Postgres failover stalls live logs (#9543) | Low / low | Fixed upstream. Restart web pods after a switchover if needed |

## 12. Open questions

1. Should Concourse be a full alternative to Tekton (the `kmt install` default switchable per environment) or an add-on only? This determines whether `--configure-tekton-pipelines` and `setup_triggers.sh` get Concourse counterparts.
2. Ingress versus tunnel by default? Tunnel mode needs `externalUrl=http://127.0.0.1:<port>`, Ingress mode needs DNS and TLS. Which should `static.json` default to?
3. Human authentication: is local users plus the admin enough, or should the Forgejo/Gitea connector be wired (OAuth app per environment)? Forgejo compatibility needs a test.
4. Kubernetes credential manager or Vault? Vault adds central rotation but makes Concourse depend on the `extra` group.
5. Where should builds run for production clusters: in-cluster privileged workers or external workers (the kwisatz Docker host / Pi)?
6. Should Concourse deploy into team namespaces with a kubeconfig/SA token (7.5), or only build and push images and leave deploys to GitOps/Tekton?
7. Is the 16K-page Pi 5 kernel acceptable, or does Kubementat require the 4K kernel on Pis?
